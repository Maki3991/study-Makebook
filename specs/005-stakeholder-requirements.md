# Spec 005 · 三方真实需求矩阵

> 目的：把消费者、工厂、平台三方的**真实世界需求**逐条摊开，每条标注三栏——
> **P0 机制**（黑客松合约/产品如何照顾）、**验证**（用哪条 FR / 不变量 / 测试证明）、**边界与路线**（没照顾到的去哪）。
> 分类口径：`[机制]` P0 已解决 · `[设计]` 设计上规避 · `[推迟]` 有意放路线图且有答 · `[不承诺]` 明确声明不做。

## 0. 需求分层总览

| 方 | 核心诉求一句话 | P0 回答一句话 |
|---|---|---|
| 消费者 | 我说愿意出多少钱，就得按不高于它的价成交，失败必须全退 | 统一清算价 + 全额预锁 + pull 退款 |
| 工厂 | 别再让我对假询盘报价，赢了必须确定收到钱 | 全部订单全额担保 + 应收清算时锁定 + claimPayout |
| 平台（我们） | 策展权在我，但钱和规则我碰不了 | 无 ownerWithdraw + Open 后全冻结 + 算法清算 |

## 1. 消费者（Buyer）

### 1.1 表达真实需求，且需求被尊重

- **真实需求**：点赞、投票、评论区都是免费信号，品牌和工厂不信。消费者里真正想要的人，希望自己的"想要"能被计入生产决策，而不是被平均掉。
- **P0 机制** `[机制]`：最高愿付价 + 同额全额预锁（deposit == maxPrice，INV-03）。表达需求的成本等于需求本身，口嗨在经济学上被消灭；每条出价都是需求曲线上的一个真实点。
- **验证**：FR-BUY-04（msg.value 严格等于 maxPrice）；CT-03（金额不符 revert）。
- **边界**：Sybil 刷量不能从技术上禁止，但刷需求 = 真金白银锁仓 + 清算成功必须真付款，成本自足 `[设计]`。

### 1.2 价格公平：不被宰，也不比别人多付

- **真实需求**：传统预售/团购里，早鸟价、杀熟、卖家临时涨价都让人不舒服；出价高的人不想当冤大头。
- **P0 机制** `[机制]`：统一清算价——所有赢家付同一个 tierPrice（R-07）；你的 maxPrice 只是上限，永远只付清算价；赢家差额 maxPrice − clearingPrice 自动可退（R-08）。
- **验证**：CT-07（maxPrice == clearingPrice 是赢家，少 1 wei 落选）；E2E-S（差额领取）。
- **边界**：统一价意味着高出价者补贴了成交规模——这是机制的有意选择（先最大化可成交人数，R-04），pitch 时主动讲 `[设计]`。

### 1.3 资金安全：平台跑路也拿得回

- **真实需求**：众筹平台暴雷、项目方失联是真实世界高频事件。
- **P0 机制** `[机制]`：资金进合约不进平台口袋；合约没有 ownerWithdraw，operator 无任何资金权限（INV-06）；失败/落选全额可领（R-08/R-10）；pull 设计使某个地址的领取失败不阻塞任何人（CT-10 恶意接收者用例）。
- **验证**：CT-04/CT-08（失败全额、重复领取拒绝）；INV-01 fuzz（余额 ≥ 全部未领负债，256 runs）。
- **边界**：智能合约自身漏洞风险残余——靠 51 个测试 + 不变量 fuzz + 无升级代理收敛；主网前需第三方审计（上主网硬门槛）`[推迟]`。

### 1.4 规则透明：我能自己验证结果

- **真实需求**："为什么我的单没成""为什么是这个价"，平台必须答得出，而不是一句"系统判定"。
- **P0 机制** `[机制]`：清算算法 R-01~R-10 公开且确定性——任何人用同一组输入手算同一结果；previewSettlement 实时预览；结果页逐条解释每个 tier 的 eligibleCount vs minQty；所有 tx 有 Blockscout 深链。
- **验证**：VIEW-05 验收（"能逐条回答为什么这个档位赢"）；附录 A.1 手算示例与合约测试一致。
- **边界**：无。

### 1.5 知情：我知道 SKU 哪来的、风险是什么、数据谁看得见

- **真实需求**：不想买到"AI 编出来"的产品；不想在不知情时暴露自己的价格意愿。
- **P0 机制** `[机制]`：每条规格可追溯到评论或标记"运营假设"（FR-AI-04）；manifestHash 证明说明书未被事后篡改；签名前必须勾选"不可撤单 + 公开性"确认（FR-BUY-05/09）；六种来源标签区分 ONCHAIN / AI / 人工确认 / 演示 / 模拟。
- **验证**：AI-01/AI-02；接口文档 2.1 节签名前文案。
- **边界**：出价公开可引发策略性跟单——签名前披露、主动接受，V2 commit-reveal `[推迟]`。

### 1.6 交易体验：出错时告诉我人话

- **真实需求**：Web3 新手面对拒签、错网、revert 会恐慌，需要知道"刚发生了什么、我的钱在不在"。
- **P0 机制** `[机制]`：错网一键切换 Chain ID 1439（FR-BUY-01）；拒签提示"链上没有产生订单"；revert 翻译成人话（19 个 custom error → 文案对照表）；Pending 防重复点击；刷新后从链上恢复订单状态（FR-BUY-06）。
- **验证**：APP-02；接口文档 2.1 revert 对照表。
- **边界**：无。

### 1.7 收到商品（履约）

- **真实需求**：众筹的终极目的是拿到东西。
- **P0 状态** `[推迟]`：testnet 原型不处理履约。Batch Receipt 是链上购买凭证（不可转让，D-14 防伪口径）；生产时间线只显示 OFF-CHAIN DEMO 标签。
- **路线**：V1 链下加密收集收货信息（工厂 KYB + 合同）；V2 里程碑托管 + 质检伙伴。
- **统一口径（PRD 未写明，本 spec 补齐）**：成功清算后买家与工厂的链下联系走"链上凭证 + V1 链下订单详情收集"两阶段；pitch 被问到不回避，直接讲这是刻意边界。

### 1.8 改主意（撤单）

- **真实需求**：消费者冲动下单后想反悔。
- **P0 状态** `[推迟]`：P0 不可撤（D-04，签名前明确警告）。理由：可撤单会让需求曲线在截止前不稳定，破坏清算的可信输入。
- **路线**：V1 撤单窗口（截止前 N 小时可撤）或 V2 commit-reveal 附带 reveal 期弃权。

### 1.9 隐私

- **P0 状态** `[机制]+[推迟]`：P0 不收集任何姓名/手机/地址（D-12），链上只有钱包假名；但出价金额公开（见 1.5）。

## 2. 工厂（Factory）

### 2.1 只面对真实需求

- **真实需求**：工厂最大的浪费是对着询价单反复报价、打样，最后客户消失。询价的转化率低到伤士气。
- **P0 机制** `[机制]`：工厂看到的不是"感兴趣人数"，而是每个价格点上**已预锁资金的订单数**（需求曲线只统计链上订单，AI 兴趣样本分开标注，PRD 14.3）。eligibleCount 里没有一条是口嗨。
- **验证**：R-02（eligibleCount 只统计 maxPrice ≥ tierPrice 的已托管订单）。

### 2.2 收款确定性：赢了就一定拿得到钱

- **真实需求**：传统预售成功后仍有尾款收不齐、买家跑单的问题。
- **P0 机制** `[机制]`：清算成功的一刻，factoryReceivable = winnerCount × clearingPrice 已在合约记账（R-09），资金早已全额托管；工厂一笔 claimPayout 领走，无账期、无追款、无跑单（CT-09：金额正确、仅中标地址、仅一次）。
- **边界**：一次性领取意味着买家承担履约风险——V2 里程碑托管（节奏）+ 工厂保证金（动机）+ 多签/质检（认定）三层解决 `[推迟]`。

### 2.3 报价效率与公平竞逐

- **真实需求**：报价一次就够；输赢规则要提前知道；不接受暗箱。
- **P0 机制** `[机制]`：Draft 期一次提交 1–3 个 MOQ 档位，Open 后冻结（FR-FAC-04）；竞逐规则公开（eligibleCount 最大 → 价低 → quoteId/tierIndex 小），输家可以验证自己为什么输；最多 2 家预审工厂，没有无限内卷。
- **验证**：CT-02（档位合法性）、CT-06（tie-break）。

### 2.4 产能敞口有界

- **真实需求**：工厂怕"爆单"——订单量超过产线能力，接了做不出来。
- **P0 机制** `[设计]`：MAX_ORDERS = 50 + 每单固定 1 件，使单个 Campaign 的最大承诺产量天然有界（≤50 件）；minQty 递增、价格递减的档位结构本身就是工厂的产能报价语言。
- **路线**：V3 显式 maxCapacity 与多工厂拆单 `[推迟]`。

### 2.5 成本变化与异常

- **真实需求**：原材料价格波动时，冻结的报价可能亏本。
- **P0 状态** `[推迟]`：Open 后报价不可改（这是消费者侧信任的代价）。缓解靠 Campaign 周期短（黑客松按小时/天计）；V1 报价有效期 + 到期重开机制。
- **统一口径**：被问到答"冻结是信任的来源，有效期是风险的出口，两者在 V1 汇合"。

### 2.6 身份、声誉与准入

- **P0 状态** `[推迟]`：P0 只有 operator 预审 + DEMO FACTORY 标签（FR-FAC-01/06）；V1 工厂签名报价 + KYB；V2 保证金 + 履约记录。

## 3. 平台 / 我们（Operator）

### 3.1 策展权：需求编译的质量由我把关

- **P0 机制** `[机制]`：选评论源、调 AI、逐项编辑候选、确认 manifest（FR-AI-06）、预审工厂、创建并开放 Campaign。AI 只是建议层，人工闸门是强制性的——未经确认不能生成 manifestHash。
- **验证**：US-O01；AI-01（无凭空新增规格）。

### 3.2 不能作恶：约束即卖点

- **P0 机制** `[机制]`：无 ownerWithdraw（INV-06）；Open 后 manifest/deadline/报价不可改（INV-04）；清算由算法执行、任何地址可触发（R-01）；平台费 P0 = 0（D-09）。
- **叙事价值**：平台跑路这个众筹最大病灶在我们结构上不存在——不是"我们不会"，是"我们不能"。

### 3.3 可持续收入

- **P0 状态** `[推迟]`：未来成功清算收 1%–3% 服务费、失败不收费；费率必须在 Campaign 开放前冻结并设硬上限（PRD 20.1）——收费规则同样接受"不可事后改"约束。

### 3.4 责任边界清晰

- **P0 机制** `[不承诺]`：平台不担保工厂履约、商品质量、物流、售后、税务（PRD 16.1 真实世界边界声明）；页面明示 DEMO/TESTNET/OFF-CHAIN 标签。
- **价值**：边界清晰不是免责话术，是评审信任的来源——每个"不做"都有对应的"谁来做、在哪个版本做"。

### 3.5 演示与评审需求（团队自身）

- **P0 机制** `[机制]`：成功/失败双 Campaign 预部署、fixture 降级（AI/网络/钱包故障不阻断演示）、Demo Panel 四种异常状态切换、证据页（tx 深链 + Blockscout）、120 秒主路径。
- **验证**：DEMO-01/02；`docs/DEMO_RUNBOOK.md`。

## 5. 已知真缺口（PRD 未写、本 spec 补齐口径）

1. **买家 ↔ 工厂的链下联系**（收货信息怎么到工厂手里）：统一答"链上凭证 + V1 链下加密收集"，见 1.7。
2. **失败 Campaign 的工厂侧善后**（报价白做了）：P0 无补偿；口径"报价成本本就极低（一次提交），失败无应收也无义务"。
3. **同一买家跨 Campaign 重复身份**：P0 不需要（单 Campaign）；V1 账户层再议。
